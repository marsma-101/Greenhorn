## 第一批：P1 对话历史

### P1-1：对话历史管理 API + 前端

**结论：✅ 可行，需补充细节**

**PI 原生数据格式**（已分析实际文件）：

会话 JSONL 文件每行一个 JSON 对象，事件类型包括：
- `session` — 会话元数据（id、timestamp、cwd）
- `model_change` — 模型切换
- `thinking_level_change` — 思考级别
- `message` — 消息（content 是数组，包含 `thinking` 和 `text` 两种 type）
- `toolResult` — 工具调用结果

**API 设计建议**（与 PM 指令基本一致，补充细节）：

| API | 说明 | 补充 |
|-----|------|------|
| `GET /api/sessions` | 列出所有会话 | 返回 `[{id, title, time, summary, messageCount}]`，加 `messageCount` 便于排序 |
| `GET /api/sessions/:id` | 加载会话消息 | 前端只展示 `user` + `assistant` 类型消息，过滤掉 thinking/tool 内部事件 |
| `DELETE /api/sessions/:id` | 删除会话 | 物理删除 JSONL 文件 |

**⚠️ 需讨论的问题**：

1. **会话列表的 title 和 summary 从哪来？**
   - PI 原生没有 title 字段，需要我们自己生成
   - 建议：取会话第一条用户消息的前 30 字符作为 title，无消息时用"空会话"

2. **sessions 目录结构**
   - PI 的会话存在 `~/.pi/agent/sessions/<cwd>/` 下，按工作目录分子目录
   - 我们是只读当前 cwd 的会话，还是合并显示所有 cwd 的会话？
   - 建议：**合并显示**，前端列表按时间排序，不区分 cwd

3. **会话 ID 是文件名还是内部 ID？**
   - PI 文件名格式：`<ISO时间>_<uuid>.jsonl`
   - 建议：用 uuid 部分作为 id，文件名只用于排序

### P1-2：对话历史保持

**结论：⚠️ 架构原则冲突，需讨论**

PM 指令中说："不需要每次对话都写 PI 文件，前端自己维护即可"

但架构原则写的是："所有数据从 PI 的原生文件读取或写入"

**两种方案供选择**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| A. 每次回复后写入 PI JSONL | 完全符合架构原则，刷新不丢数据 | 需要实现 JSONL 写入逻辑，较复杂 |
| B. 前端 localStorage 保存 | 简单，实现快 | 违背架构原则，换浏览器/设备就丢 |
| C. 前端维护 + 后端定期保存 | 兼顾体验和持久化 | 实现复杂度中等 |

**💡 推荐方案 A 的简化版**：
- 不需要像 PI 那样写完整的 JSONL 事件流
- 维护一个简化的 session 映射文件 `~/.pi/agent/sessions-greenhorn/<sessionId>.json`
- 每次消息追加写入，格式简化为 `[{role, content, timestamp}]`
- 读取时直接返回，不依赖 PI 原生文件

这样既保持了"数据通过后端读写文件"的架构，又不强行兼容 PI 复杂的 JSONL 格式。

## 第二批：P2

### P2-1：文件选择器

**结论：✅ 可行，需加限制**

**💡 技术建议**：
- 单文件大小限制：**500KB**（过大的文件会撑爆 context）
- 支持类型：`.txt`, `.md`, `.json`, `.js`, `.ts`, `.py`, `.sql`, `.html`, `.css`, `.xml`, `.yaml`, `.csv` 等文本文件
- 发送时将文件内容作为 `system` 消息注入（不是 `user` 消息），格式：

```
system: 用户上传了文件 {filename}，内容如下：
---
{file content}
---
请基于以上文件内容回答用户的问题。
```

- 二进制文件（.exe, .pdf 等）显示 "不支持的文件类型" 提示，不发送

### P2-2：智能体设定

**结论：✅ 可行**

**实现方案**：
- 设置页新增「智能体设定」区域

- 对话时在 system prompt 前部注入：

```

用户消息：...
```

- 预设模板存储在前端常量，用户选模板时填入 textarea，可以再编辑

## 技术风险提示

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| PI 升级导致会话格式变化 | 会话 API 解析失败 | 解析层做 try-catch，格式异常时返回空列表 |
| 大文件上传导致 context 超限 | 对话质量下降 | 后端截断文件内容，超过 20000 字符时只保留前 10000 + 后 5000 |
| 并发写入 session 文件 | 数据竞争 | 用文件锁或简单的 append-only 策略 |
| sessions 目录不存在 | 列表为空 | 启动时自动创建目录 |
