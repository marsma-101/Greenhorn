## 一、核心决定：废弃独立文件，直接用 PI 原生

**否决你方案中的「双写」和 `sessions-greenhorn/` 目录。** 采用单一数据源架构：

```
后端 /api/sessions 系列接口
    ↓
直接读写 PI 原生会话文件：~/.pi/agent/sessions/*.jsonl
    ↓
前端 API 接口不变，展示不受影响
```

**理由**（用户明确要求）：
1. PI 原生格式数据更全（含思考过程、工具调用、token 用量）
2. 单一数据源，**不存在同步问题**——两边内容天然一致
3. 换引擎兼容：将来接其他智能体，只换后端读取逻辑，前端零改动
4. 符合"不自己造轮子"原则

## 二、方案细节

### 2.1 jsonl 文件位置与命名

| 项 | 规范 |
|----|------|
| 目录 | `~/.pi/agent/sessions/--路径--/`（与 PI 原生一致，按 cwd 分目录） |
| 文件名 | `<ISO时间>_<uuid>.jsonl`（严格按 PI 原生命名） |
| cwd 路径 | **start.bat 所在目录**（用户启动 GreenHorn 的目录） |
| 写入模式 | append-only 追加，不复写全文件 |
| 行格式 | 严格遵循 PI 官方规范（session / message 事件，content 是数组） |

### 2.2 会话标题单独存放

PI 原生 jsonl **没有标题字段**，但用户需要"会话改名"功能。方案：

- 对话内容 → 只存在 PI 原生 jsonl（唯一数据源）
- 标题映射 → 单独一个元数据文件：`~/.pi/agent/sessions-greenhorn-meta/titles.json`
  ```json
  {
    "<sessionId>": { "customTitle": "用户改的名字", "updatedAt": "..." }
  }
  ```
- 读取会话列表时：优先用元数据里的自定义标题，没有则取第一条用户消息前 30 字
- 改名 → 只写元数据文件，不碰 jsonl

### 2.3 旧会话迁移

`sessions-greenhorn/` 里已有的 2 个会话（2026-07-30）必须迁移到 PI 原生 jsonl：
- 读取旧 json → 生成 PI 原生格式 jsonl → 写入 `sessions/--路径--/`
- 迁移完成后旧目录可保留（不再读写）

### 2.4 删除会话

删除 = 删除对应 jsonl 文件 + 元数据文件中的条目。

### 2.5 容错

jsonl 读写异常时：返回空列表/空会话给前端，不崩溃，console.error 记录。
