## 二、问题清单

### ❌ 问题 1（致命）：message 行结构不符合 PI 规范

**PI 官方规范**（`docs/session-format.md` 第 202-207 行，附真实文件对照）：

```json
{"type":"message","id":"c346df82","parentId":"b5cf99e3","timestamp":"2026-06-30T05:37:48.106Z","message":{"role":"user","content":[{"type":"text","text":"怎么打开的是你？"}],"timestamp":1782797868102}}
```

关键：`role` 和 `content` 必须**嵌套在 `message` 对象内部**（这个 `message` 字段就是 AgentMessage 对象）。

**你当前写的**：

```json
{"type":"message","id":"7288069b-7d67-42ad-b290-0de442b4b6d6","parentId":null,"role":"user","content":[{"type":"text","text":"你好世界"}],"timestamp":"2026-07-31T04:09:08.050Z"}
```

`role`/`content` 在顶层，**没有 `message` 嵌套**。

**修改原因**：PI 的解析器（`buildSessionContext()`）从每个 entry 中读取 `entry.message.role` / `entry.message.content`。没有嵌套，解析会得到 undefined，**整个会话在 PI 里读不出来或消息丢失**。这是"格式看起来对、实际读不了"的典型情况。

**正确格式**（user 消息）：
```json
{"type":"message","id":"<uuid>","parentId":"<父id>","timestamp":"<ISO>","message":{"role":"user","content":[{"type":"text","text":"<内容>"}],"timestamp":<epoch毫秒>}}
```

**正确格式**（assistant 消息，比 user 多了 provider/model 等字段）：
```json
{"type":"message","id":"<uuid>","parentId":"<父id>","timestamp":"<ISO>","message":{"role":"assistant","content":[{"type":"text","text":"<内容>"}],"provider":"ollama","model":"qwen3.5:9b","timestamp":<epoch毫秒>}}
```

### ❌ 问题 2（方案优化）：用 PI 原生 session_info 存标题，废弃 titles.json

**重大发现**：PI 原生支持会话名称存储！`docs/session-format.md` 第 283-291 行：

```json
{"type":"session_info","id":"<uuid>","parentId":"<父id>","timestamp":"<ISO>","name":"改的名字"}
```

- 通过 PI 的 `/name` 命令设置
- `/resume` 会话选择器会**直接显示这个名字**
- 我们读写它完全符合 PI 规范

**修改原因**：你之前建的独立 `titles.json` 属于"自己造轮子"。用 PI 原生的 `session_info` 事件，会话名会直接出现在 PI 的 `/resume` 里，数据全在 PI 文件内，更符合"单一数据源 + 不自己加功能"原则。

**需要改**：
1. 删除 `titles.json` 元数据文件逻辑
2. 改名 → 往 jsonl 追加一行 `session_info` 事件
3. 读取会话列表 → 从 jsonl 中找 `session_info` 的 `name`，有就用，没有则取第一条 user 消息前 30 字
