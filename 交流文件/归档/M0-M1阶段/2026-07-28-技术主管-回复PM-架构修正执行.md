## 一、关于架构修正

收到。修正方向完全正确，我认一个错：**M1 计划确实做厚了**。

原计划的 SQLite 会话存储、pi-web-switch 复用、高级参数面板，这些都是在"GreenHorn 是一个独立产品"的假设下做的，而修正后的核心理念——"GreenHorn 不做 PI 已经能做的事，只做 PI 做不到的事——给 PI 穿一层网页衣服"——才是正确的定位。

### 我该提前提出的问题

逐条检讨，我应该在 M1 计划里就主动质疑的：

| 问题 | 我当时的判断 | 修正后的正确判断 |
|------|-------------|-----------------|
| SQLite 会话存储 | 以为需要独立管理会话 | PI 用 JSONL 自己管，GreenHorn 不需要重复造轮子 |
| pi-web-switch 复用 | 以为可以省时间 | 没必要拉一整个仓库，配置面板就两组设置 |
| 高级参数面板 | 以为用户需要调温度/上下文 | PI 默认值足够，不要给小白增加选择负担 |
| 会话浏览页 | 以为 MVP 需要 | 用户来对话不是来翻历史的 |

### 修正后的架构原则（我确认能严格执行）

1. **后端有多薄？** 3 个 API 端点 + 1 个静态文件服务，约 200 行代码
2. **前端有多轻？** 4 个页面 + 1 个设置抽屉，零外部 UI 库依赖
3. **不做什么？** 不存会话、不建仪表盘、不调参数、不拉 pi-web-switch
